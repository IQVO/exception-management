warehouse.exception-management.events.

The six fact consumers are always ON (no *_MODE exists in this service):
  group {{ .Values.config.fulfillmentExceptionsConsumerGroup }}     <- warehouse.fulfillment.events
  group {{ .Values.config.workPlanningExceptionsConsumerGroup }}        <- warehouse.work-planning.events
  group {{ .Values.config.networkFulfillmentExceptionsConsumerGroup }} <- warehouse.network-fulfillment.events
  group {{ .Values.config.orderCorrelationConsumerGroup }}      <- warehouse.order-management.events (auto-resolve correlation)
  group {{ .Values.config.inventoryExceptionsConsumerGroup }}         <- warehouse.inventory.events
  group {{ .Values.config.returnsExceptionsConsumerGroup }}           <- warehouse.returns-processing.events
  group {{ .Values.config.cartonDiscrepancyConsumerGroup }}           <- warehouse.inbound-receiving.events

/readyz answers 503 until Postgres answers and a Kafka broker answers a
metadata request. Topics are not checked: the relay's writer auto-creates the
service's own topics on first write (fleet convention), the service never
creates them through an admin API, and a consumed topic that does not exist
yet shows as consumer retry logs, not as unreadiness.
